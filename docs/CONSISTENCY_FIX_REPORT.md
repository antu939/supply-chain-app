# 一致性、安全性及交互稳定性修复记录

## 本轮修复

| 领域 | 修复内容 |
| --- | --- |
| 数据一致性 | BOM 保存前比较本机原始记录与当前窗口已读取版本；发现外部更新时拒绝覆盖，提示用户重新加载。 |
| 数据保护 | BOM 本地记录读取异常时禁止常规操作写入，保留原始数据；仍支持用户明确确认后由备份恢复。导入前备份原始保存内容，而非可能过期的内存工作区。 |
| 交互稳定性 | BOM 保存失败时恢复变更前的业务状态及界面选择；失败的操作不进入撤销记录，撤销、重做和拖拽失败也不会推进历史或虚报成功。 |
| 索引一致性 | 本机查询索引按当前原始数据重新生成，不依赖可能重复的 BOM counter / Sales revision。支持物理分区提供者的读取路径不变。 |
| 记录归档 | 月份必须为有效的 YYYY-MM，修复旧记录归档月份无效时分区与记录内部 originMonth 不一致的问题。 |
| 数据读取 | 当前销售数据损坏时不再以旧版本数据替代；总览识别非法根结构与 BOM 空记录项，显示读取异常而不是崩溃。 |
| 模块同步 | 切回销售模块时检测外部存储更新并加载新工作区，重新计算结果。重新加载成功后清除过期编辑弹窗及历史，失败时保留最后可用状态。 |
| 通信边界 | 限制外壳与模块之间的消息为实际对应的框架、约定的声明来源和同源（HTTP）发送者。 |
| 交互反馈 | BOM 与 Sales 各自记录保存状态，避免另一模块成功保存掩盖当前模块错误；快速切页时跳过尚未发送的过期导航。 |

## 验证

新增 `tests/consistency-regression.js`，覆盖保存失败、撤销历史、跨窗口数据更新、异常读取与明确恢复、索引刷新、旧版数据兼容及归档月份一致性。扩充 `tests/stage2-check.js`，验证销售模块重新进入后确实读取外部已保存的新版本。

在项目根目录用 Node.js 执行所有回归脚本：

```sh
for t in tests/*.js modules/bom/tests/regression.js modules/sales/tests/engine.test.js; do
  node "$t" || exit 1
done
```

浏览器执行环境缺少可运行的 Chromium，不能在本次环境中完成真实浏览器 iframe 端到端验证。建议按 README 启动本地 HTTP 服务，在实际使用浏览器中复查：

1. 新建 BOM、编辑公司、拖拽组件、撤销/重做后刷新，确认数据保留。
2. 同一浏览器开两个标签页，在一页修改 BOM，另一页继续编辑时应提示重新加载；刷新后再操作。
3. 跨 BOM 与销售模块切换，在销售模块数据已被其他标签页更新时确认重新加载且显示最新记录。
4. 通过备份恢复和 AI 助手写入后确认总览统计与查询结果保持一致。

## 兼容性

未引入第三方依赖，也未改变已有业务存储键、BOM/Sales 数据版本或业务模型。本地查询索引仍可从原始数据重建。建议在替换旧代码前导出 BOM 和销售模块各自的 JSON 业务备份，并保持相同 HTTP 地址和端口，避免浏览器同源存储隔离造成“数据消失”的误解。
